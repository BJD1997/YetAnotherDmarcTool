## 1. Per-domain trend

### Goal
Show whether a domain's DMARC pass rate is trending up, stable or trending down, without false alarms on low-volume domains. A drop that persists becomes an Action queue item.

### Calculation (per domain, daily)
- **Recent window:** last 7 days. **Baseline window:** the 28 days before that.
- Both use the same message population as the domain rating (`windowed_totals_excluding_blocked`: blocked senders excluded, unverified reports excluded by the ORM filter), bucketed per day on `date_range_begin`.
- **Trending down** when all three hold:
  1. **Significant:** a one-sided two-proportion z-test of the recent pass rate against the baseline gives z ≥ 1.96.
  2. **Material:** recent pass rate is at least **2 percentage points** below the baseline.
  3. **Persistent:** on at least **3 distinct days** in the recent window, that day's pass rate is below the baseline pass rate (days with no mail don't count either way).
- **Trending up:** the mirror image (z ≤ −1.96, ≥ 2 points above, ≥ 3 days above).
- **Insufficient data:** fewer than **20 messages** in either window, or fewer than 3 days with mail in the recent window.
- **Stable:** otherwise.
- Worked example: 4 mails a day, 2 failures on one day. One day below baseline, so rule 3 fails and it isn't trending down, however significant. The same failures on 3 or more days trigger it.

### Storage
New table `domain_trends` (one row per domain, replaced on each computation): `domain_id` (PK, FK), `organization_id`, `state` (`up`/`stable`/`down`/`insufficient_data`), `recent_pass_pct`, `baseline_pass_pct`, `recent_messages`, `baseline_messages`, `days_below`, `days_above`, `computed_at`. RLS like every other org-scoped table.

### Computation
A worker job `trend_refresh`, enqueued by the leader every 6 hours for each domain with traffic in the last 35 days. The pure calculation lives in `app/services/rating/trend.py` (`compute_trend(days: list[DayCounts], today) -> TrendResult`), unit-tested without a database.

### UI
- **Domain page (overview tab):** a trend line: "Trending down: 91.2% this week, 99.1% the 4 weeks before", with an up/down/flat icon and a "not enough mail yet" state.
- **Action queue:** for `state = down`, a `serious` item "`<domain>`: pass rate down from 99.1% to 91.2% this week", linking to `/domains/{id}/senders?filter=failing`.

## 2. Notifications bell

### Goal
Surface things the reports turn up (new domains, new DKIM selectors) to everyone in the organization at sign-in, stored rather than recomputed on every page load.

### Data model
New table `notifications`: `id`, `organization_id`, `kind` (`domain_detected` / `dkim_selector_detected`), `subject_key` (unique per org and kind: the domain name, or `domain_id:selector`), `domain_id` (nullable), `payload` (JSONB: message volume, selector, signing sender's service label), `created_at`, `resolved_at`, `resolved_reason` (`handled` / `dismissed`), `resolved_by` (nullable user). Unique `(organization_id, kind, subject_key)`. RLS.

### Producing notifications
- A worker job `notifications_refresh` per organization, enqueued after each mailbox poll and every 10 minutes by the leader.
- **Domain detected:** the detected-domains logic (`_detected_domain_items`, factored out of `GET /dmarc/detected-domains`). Insert any name not already present (ON CONFLICT DO NOTHING). A dismissed detected domain is never notified.
- **DKIM selector detected:** the org-wide grouped selector query (`recent_dkim_selectors_for_org`, last 30 days, aligned DKIM only, not already monitored). The payload carries the service label of the sender that signed with it, taken from the records' source IPs (`SourceIpIdentity`), highest volume first.
- **Auto-resolve** in the same job: domain notifications whose name is now registered or dismissed, and selector notifications whose selector is now monitored. Resolved with `handled`.

### API
- `GET /api/notifications`: open notifications first, then the last 20 resolved. Any org member.
- `GET /api/notifications/count`: open count, for the dot (polled every 60 s by the shell).
- `POST /api/notifications/{id}/dismiss`: org admins.

### Links
- **Domain detected:** `/settings/domains` (Add / Dismiss live there).
- **DKIM selector detected:**
  - if the signing sender's review status for that domain isn't `approved`: `/domains/{id}/senders?highlight=<service label>` (approve or reject first);
  - otherwise `/domains/{id}/dns?open=dkim-selectors`. This is a new deep link: it scrolls to and highlights the DKIM selectors block, the same way `?open=policy-builder` opens the Policy Builder.

### UI
A bell button in the sidebar header (desktop) and the mobile top bar, with a red dot when the open count is above zero. It opens a panel listing notifications with their text, age and link; admins see a dismiss button. Members see the same list; links work, actions on the target pages stay admin-only as they are today.

## 3. Ask AI

### Goal
Turn an issue into a ready-made prompt for an AI assistant, opt-in per organization.

### Setting
`organizations.ask_ai_enabled` (bool, default false). Org admins toggle it in Settings → General, and the onboarding wizard gets a short step offering it, with a one-line explanation of what is shared.

### Prompt building (backend)
`GET /api/ask-ai/prompt?kind=<kind>&domain_id=…&subject=…` returns `{prompt}`; 404 when the org hasn't enabled it. Kinds:
- `dns_check`: domain, check type, current record text, the finding, the domain's mail profile.
- `sender_alignment`: domain, sender service label, its IPs with reverse DNS, SPF/DKIM pass rates, SPF and DKIM domains seen in reports, volume, the domain's current SPF record.
- `compliance`: pass rate, the 3 worst senders with their numbers, current policy, volume (also used for "not ready to tighten" and "trending down").

Every prompt starts with a fixed instruction (step-by-step fix, explain why, DNS record examples). It never includes organization names, user emails, mailbox or reporting addresses, or raw reports. A test asserts this for every kind.

### UI
An "Ask AI" button on Action queue items, on failing/warning DNS check findings, and on sender rows with failing alignment, shown only when enabled. It opens a dialog with the prompt (read-only text) and buttons: **Open in Claude** (`https://claude.ai/new?q=`), **Open in ChatGPT** (`https://chatgpt.com/?q=`), **Copy and open Gemini** (`https://gemini.google.com/app`), **Copy prompt**. Prompts are kept under 6,000 characters so the links work in all browsers.

## 4. STARTTLS from TLS-RPT reports

### Setting
`STARTTLS_CHECK_MODE` = `probe` (default) / `tls_rpt` / `off`. `STARTTLS_CHECK_ENABLED=false` still works and means `off`. The Azure template parameter becomes `starttlsCheckMode`, default `tls_rpt`. The old `enableStarttlsCheck` stays accepted (`true` maps to `probe`), so existing parameter files still deploy. The template sets `STARTTLS_CHECK_ENABLED=true` next to the mode, so a v0.1.7 `false` can't override it.

### Per-domain result in `tls_rpt` mode
Uses the domain's TLS-RPT reports from the last 14 days (summary counts per report, failure details with `receiving-mx-hostname` and `result-type`):
- **TLS-RPT doesn't reach the app** (`check_tls_rpt_rua_destination` says the domain's `rua=` doesn't include its hosted address or the org mailbox): no finding, so it's left out of the grade. No separate hint: the TLS-RPT check already warns when the record is missing or points elsewhere.
- **Reaches the app, no reports yet:** a new `pending` status, "Waiting for TLS-RPT reports". Neither pass nor fail, left out of the grade.
- **Reports present:**
  - `pass` when successful sessions > 0 and failures ≤ 2% of all sessions;
  - `warn` when failures > 2%, listing the MX hosts and failure types;
  - `fail` when failures > 0 and successful sessions = 0.

### Status enum
`CheckStatus` gains `pending`. Scoring ignores it like a missing check; `worst_status` ranks it below `pass`. The frontend gets a neutral "Pending" badge.
