# v0.2.0-beta2: per-organization rating window + per-domain trend — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the 90-day rating window a per-organization setting (30/60/90/180), and add a volume-aware per-domain trend that shows on the domain page and raises an Action queue item when a domain trends down.

**Architecture:**
- **Rating window:** `organizations.rating_window_days` is read by one helper, `rating_window_days(db, organization_id)`. `_windowed_totals` and the Action queue use it instead of the `RATING_WINDOW_DAYS` constant (which stays as the default).
- **Trend:** a pure `compute_trend()` over per-day counts; a singleton worker job `trend_refresh` every 6 hours writes one `domain_trends` row per domain. The Action queue and the domain page read that row.

**Tech Stack:** FastAPI, SQLAlchemy async, Alembic, Postgres RLS; React/TS + vitest.

**Spec:** `docs/superpowers/specs/2026-10-02-v0.2.0-design.md` §1 and §5

## Global Constraints

- Branch `v0.2.0-beta`. Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. No new dependencies.
- Rating window values: **30, 60, 90, 180**; default **90**.
- Trend (verbatim from spec): recent **7 days** vs baseline **28 days before**; down when z ≥ **1.96** (one-sided two-proportion test), at least **2 percentage points** lower, and below baseline on at least **3 distinct days** with mail; mirror for up; **insufficient data** under **20 messages** in either window or fewer than 3 days with mail in the recent window.
- Same message population as the rating: `windowed_totals_excluding_blocked` semantics (blocked senders excluded, unverified reports excluded by the ORM filter), bucketed by `date_range_begin` day.
- Every new org-scoped table gets RLS like the others (see `0001_initial_schema.py`'s policy helper and the latest migration that added an RLS table).
- Tests: backend `TEST_DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:55432/dmarc_test PYTHONDONTWRITEBYTECODE=1 python3 -m pytest -q -p no:cacheprovider` from `backend/`; frontend `npx tsc -b && npx vitest run`.

### Task 4: `compute_trend` (pure)

**Files:** Create `backend/app/services/rating/trend.py`; Test `backend/tests/services/rating/test_trend.py`.

**Interfaces:**
- `@dataclass DayCounts(day: date, total: int, passed: int)`
- `@dataclass TrendResult(state: Literal["up","stable","down","insufficient_data"], recent_pass_pct: float | None, baseline_pass_pct: float | None, recent_messages: int, baseline_messages: int, days_below: int, days_above: int)`
- `compute_trend(days: list[DayCounts], today: date) -> TrendResult`. Recent = `today-6 … today`; baseline = `today-34 … today-7`.

- [ ] **Failing tests (each a case from the spec):**
  - **Quiet server, one bad day:** 4 mails/day, baseline all passing, 2 failures on 1 recent day → `stable`, `days_below == 1`.
  - **Quiet server, persistent:** 2 failures on each of 3 recent days → `down`.
  - **Chatty server, one-day dip:** 400/day, 120 failures on 1 day → `stable`.
  - **Chatty server, persistent drop:** 400/day, 40 failures on 5 days vs ~0 → `down`.
  - **Small real dip:** 99.9% → 99.7% on a chatty server (under 2 points) → `stable`.
  - **Up:** baseline 85%, recent 99% on 4+ days → `up`.
  - **Insufficient data:** 10 messages in the recent window → `insufficient_data`.
- [ ] **Implement:**
  - z statistic: `(p_base - p_recent) / sqrt(p_pool*(1-p_pool)*(1/n_base + 1/n_recent))`, with `p_pool` the pooled rate;
  - guard against a zero denominator (both rates 0 or 1: z = 0);
  - `days_below` counts recent days with mail whose own rate < `p_base`; `days_above` mirrors it.
- [ ] Tests pass. **Commit** "Trend calculation: significant, material and persistent".
